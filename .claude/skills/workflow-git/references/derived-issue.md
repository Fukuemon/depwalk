# 派生 Issue (前段 phase の取りこぼし) の起票規律

設計中・実装中に「本来は前段の phase で拾われているべきだった追加要求・仕様」が発覚したとき、
**進行中の issue / spec を書き換えず、新規 issue (= 派生 issue) を起票**して品質ラベルを付与する。
後戻り要求を会話の中で握り潰さず、トレース可能な形で残すのが目的。
ラベル値と色の正本は `context/project.yml` の `labels` (`quality:*` 軸)。

## 判定表 (どこで発覚したら対象か)

| 進行中 phase | 発覚した内容                     | 扱い                                             |
| ------------ | -------------------------------- | ------------------------------------------------ |
| 要求整理中   | 要求の論点追加・追記             | **対象外** (同一 issue で吸収)                   |
| 設計中       | 要求側で書かれているべき要件     | **対象**: 派生 issue + `quality:requirement-gap` |
| 設計中       | 設計判断の修正・補強             | **対象外** (同一 spec で吸収)                    |
| 実装中       | 要求側で書かれているべき要件     | **対象**: 派生 issue + `quality:requirement-gap` |
| 実装中       | 設計側で仕様化されているべき内容 | **対象**: 派生 issue + `quality:design-gap`      |

両方に該当する場合は `quality:requirement-gap` を優先する (根本原因の早い段階に倒す)。

## 検知時の停止 + 確認 (承認の取り方に従い 3 択で提示)

```text
【前段 phase の取りこぼしを検知しました】
発覚 phase: {設計中 / 実装中}
内容: {追加要求 / 仕様の概要}
判定: quality:requirement-gap / quality:design-gap / 同一 issue で吸収

対応を選んでください:
  A) 派生 issue を起票する (推奨。品質ラベル付き)
  B) 既存 issue / spec 内で対応する (理由必須。該当 issue にその判断を記録)
  C) 保留 (要件の決定者に確認)
```

## 派生 issue 起票時の必須事項

1. **品質ラベルを 1 つだけ付与** (`quality:requirement-gap` または `quality:design-gap`)
2. **本文に「変更元」セクション** (発覚理由は空欄禁止):

   ```markdown
   ## 変更元

   - 変更元 Issue: #{番号}
   - 発覚 phase: 設計中 / 実装中
   - 発覚理由: {なぜ前段 phase で取りこぼしたかの簡潔な振り返り}
   ```

3. **変更元 issue へ逆リンク**: 変更元 issue 本文の末尾に `## 派生 Issue` セクションを設け、
   派生 issue へのリンクを追記する (双方向リンク)
4. 通常の起票規律 (`issue-format.md` / `issue-workflow.md`: type / domain ラベル、テンプレート) は
   派生 issue にも同様に適用する

## 起票後の進行中作業への反映

- **設計中に検知した場合** (`spec-lifecycle`): 該当論点を spec の論点テーブルに
  「保留 (派生 issue: #{番号} の解決待ち)」と記録し、その論点の確定は派生 issue 側に委ねる
- **実装中に検知した場合**: 進行中の実装スコープには含めず、派生 issue を後続作業とする
- 選択 B (既存内で吸収) の場合は、その判断と理由を該当 issue のコメントに記録する
