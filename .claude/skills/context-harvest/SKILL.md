# Context Harvest

作業中に得た知見のうち、**今回の issue が閉じても価値が残るもの** を durable な文書 (context / feature doc / ADR) に書き戻す skill。
会話の中だけに知見が残ると、次の作業で同じ調査・同じ失敗を繰り返す。

## いつ使うか

- 実装・レビュー・障害対応の締めくくり (PR 作成前後)
- 作業中に「これは次もハマる」「文書に書いてない前提だった」と気づいた
- 同じ説明を会話で 2 回以上した (= 文書に書き戻すべきサイン)
- `spec-lifecycle` の sync phase が対象外とした「設計以外の知見」を残したい

## 先に読むもの

- `AGENTS.md` の `Spec Workflow Contract` — 正本境界 (どの文書がどの情報の正本か) と「文書メタ情報の同期」
- `context/project.yml` と既存の `context/*.md` — 追記先の候補と既存記述 (重複防止)
- `styleguide-documents` skill — 書き戻す文章の品質基準

## 入力

- 対象の知見 (指定がなければ会話と diff から候補を抽出して提案する)
- 追記先の指定 (任意。なければ下の判定表で提案する)

## 実行フロー

### 1. 知見の抽出

会話・diff・レビュー指摘から候補を列挙する。書き戻す対象は次を満たすものだけ:

- **横断的**: 今回の issue 固有ではなく、将来の別作業でも判断材料になる
- **再導出できない**: コード・git log・既存文書を読むだけでは分からない (ハマりどころ、暗黙の前提、試して駄目だった方法)

issue 固有の決定は spec に残す (本 skill の対象外。`Spec Workflow Contract` の正本境界)。

### 2. 書き戻し先の判定

| 知見の種類                                     | 書き戻し先                    |
| ---------------------------------------------- | ----------------------------- |
| 技術規約・環境・コマンド・テストのハマりどころ | `context/<topic>.md`          |
| 特定 feature の設計前提・データ構造の注意点    | feature doc                   |
| 技術選定・不可逆な判断とその理由               | ADR (新規)                    |
| skill / rule 自体の不具合・改善                | `skill-feedback` skill へ切替 |
| 今回の issue でしか使わない決定                | spec (書き戻さない)           |

- 既存 topic への追記を新規ファイル作成より優先する。
- 新規 `context/*.md` の追加、および ADR の新規作成はユーザーに確認してから行う。

### 3. 書き戻し

- `styleguide-documents` の原則に従い、条件・理由・判断基準まで書く (「注意する」だけの行を足さない)。
- 既存記述と重複・矛盾する場合は追記でなく該当箇所を更新する。
- `Spec Workflow Contract` の「文書メタ情報の同期」に従い、対象文書のメタ情報も更新する。

### 3-2. 読み取り索引 (`context/impact-index.yaml`) の更新

書き戻した知見が特定 feature に紐づく場合、索引の該当エントリを同時に更新する:

- 該当エントリの `read:` に書き戻し先ファイルが含まれているか確認し、無ければ足す
- 新しい feature ならエントリを新設する (`coverage: partial` で仮置きしてよい)
- 書き戻しで context が揃った feature は `coverage: partial` → `full` に上げる

索引が実態とずれると読み取り契約 (索引 → `read:` だけを読む) が壊れ、全文読みに逆戻りする。

### 4. ユーザー報告

- 書き戻した知見と反映先の一覧
- 対象外とした候補とその理由 (issue 固有 / 再導出可能)

## 停止条件

- 知見が issue 固有か横断的か判定できない (推測で context に書かない)
- 新規 context ファイル / 新規 ADR の作成にユーザーの確認が得られていない
- 書き戻す内容が既存の context / Design Doc / ADR と矛盾する (先に `spec-lifecycle` の sync phase や ADR 更新を提案する)
- プロダクトの意思決定 (仕様変更・方針変更) を含む — 知見の記録ではなく設計判断としてユーザーに返す
