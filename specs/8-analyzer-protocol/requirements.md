## 背景・目的

depwalk は Core を言語非依存に保ち、言語ごとの解析差を独立プロセスの Analyzer に閉じ込める (P1〜P4)。その結合点が **Analyzer SPI + Communication Protocol (JSONL) + Model (`MethodSymbol` / `CallEdge` / `SourceLocation`)** である。この共通契約を確定することで、新言語の Analyzer を Core 変更なしに追加できる (S5)。本 feature は全 analyzer が実装する **durable な契約の正本**。

関連: [design/DesignDoc.md](../../design/DesignDoc.md) Communication Protocol、設計原則 P3/P4、モジュール責務 (Model / Analyzer SPI)、Alternatives (A2/A3)、Future Work Phase1/Phase5。

## 想定ユーザー/ステークホルダー

- Core 開発者: Analyzer の内部を知らずに `CallEdge` / `MethodSymbol` のみを受領したい
- Analyzer 実装者 (Java / 将来 Kotlin/TS/Go): 準拠すべきスキーマ・通信仕様を一意に知りたい

## 提供価値(成功条件)

| #   | 成功条件                                                 | 測定方法                                                            |
| --- | -------------------------------------------------------- | ------------------------------------------------------------------- |
| S5  | 新しい言語の Analyzer を追加するとき Core を変更せず済む | Analyzer 追加で Core モジュールに差分が出ない (Protocol のみで結合) |

## スコープ

### やること

- Model スキーマ定義: `MethodSymbol` / `CallEdge` / `SourceLocation` (Q1)
- Communication Protocol: STDIN/STDOUT 上の JSONL (1 行 1 レコード) の要求/応答仕様
- Analyzer SPI: Core が Analyzer をプラグインとして扱う境界の定義
- バージョニング / 後方互換の方針 (新フィールド追加が容易であること)

### やらないこと

- 特定言語の解析実装 (→ `java-analyzer` ほか言語別 Analyzer)
- グラフ探索 (→ `traversal`)、出力整形 (→ `output`)

## 業務ルール

| #   | ルール                                                            | 理由                            | 備考           |
| --- | ----------------------------------------------------------------- | ------------------------------- | -------------- |
| R1  | Core は Analyzer 内部 (使用ライブラリ・言語ランタイム) を知らない | 結合点の最小化 (P3)             | DesignDoc      |
| R2  | Analyzer は本契約の Model / Protocol にのみ依存する               | 言語追加で Core 無変更 (P4, S5) |                |
| R3  | スキーマは新フィールド追加が容易な形 (前方互換) を保つ            | 拡張容易性                      | JSONL 採用理由 |

## 入出力要件

### 入力 (Core → Analyzer)

| #   | 項目     | 必須/任意 | 形式  | 制約/備考                       |
| --- | -------- | --------- | ----- | ------------------------------- |
| I1  | 解析要求 | 必須      | JSONL | 対象 / 解析範囲の指定 (詳細 Q1) |

### 出力 (Analyzer → Core)

| #   | 出力             | 条件   | 備考                                     |
| --- | ---------------- | ------ | ---------------------------------------- |
| O1  | `MethodSymbol`   | 解析時 | メソッドの同定情報 (Q1 でフィールド確定) |
| O2  | `CallEdge`       | 解析時 | 呼び出し関係 (caller → callee)           |
| O3  | `SourceLocation` | 解析時 | ソース位置情報                           |

## 例外シナリオ

| #   | シナリオ                       | ユーザーへの見せ方              | 代替手段                       |
| --- | ------------------------------ | ------------------------------- | ------------------------------ |
| E1  | Analyzer が不正な JSONL を返す | パースエラーを報告し中断        | スキーマ検証で早期検出         |
| E2  | Analyzer プロセスが異常終了    | 終了コード / stderr を伝播      | プロセス境界でのエラー伝播仕様 |
| E3  | 未知フィールドを含むレコード   | 既知部分を採用し無視 (前方互換) | バージョニング方針 (R3)        |

## バリデーション方針（業務観点）

| #   | 対象       | ルール                         | エラー時の扱い         |
| --- | ---------- | ------------------------------ | ---------------------- |
| V1  | JSONL 各行 | 定義スキーマに準拠していること | 不準拠行は報告して拒否 |

## 権限要件

- 非該当 (CLI ツール)。

## 監査/非機能要件

### 監査・運用

- JSONL はテキストで観測可能。Core ↔ Analyzer の通信をデバッグ時に追跡できること (デバッグ容易性)。

### 非機能(性能/可用性/セキュリティ/保守)

- 1 行 1 レコードのストリーミングで大規模出力に耐えること。
- スキーマはバージョンを持ち、後方/前方互換の方針を明示する。
