## 背景・目的

実装が Phase1 の主要機能まで到達した一方、**文書とコードの言語・内容の両面で実態との乖離が蓄積している**。

### 文書内容の乖離 (2026-07-26 実測)

`README.md` は設計フェーズ当時のまま更新が止まっている。

- Status が「設計フェーズ (Draft) — 実装は未着手」だが、Core / Java Analyzer とも実装済みで CI も稼働している (`README.md:5`)
- **存在しない `context/project.md` を 2 箇所で参照**している (実ファイルは `context/project.yml`。`README.md:5,65`)
- ディレクトリ一覧に **実装の本体である `core/` と `analyzers/` が載っていない**。`testdata/` `scripts/` も欠落している (`README.md:74-82`)
- doc map が `design/features/` を「未着手」、`adr/` を「未着手」と記載しているが、feature doc は 6 本 (1,805 行)、ADR は 7 本が存在する (`README.md:63,66`)
- 「設計フェーズの進行」表が #6〜#9 の 4 件しか載せておらず、その後の #11 / #12 / #21 / #22 / #24 / #27 / #32 / #34 / #35 が反映されていない (`README.md:47-54`)

### 文書構造の課題

- 索引が `README.md` / `context/README.md` / `adr/README.md` / `design/features/README.md` の 4 箇所に分散し、どれが入口か読み手が判断できない
- `specs/` が「issue close 時に削除する作業文書」であることは契約に書かれているが、close 済み issue の spec が 10 本残っており、契約と実態が乖離している (closeout 未実行)
- 文書の層 (Why/What / How-landscape / How-feature / How-規約 / 意思決定 / 作業文書) は定義済みだが、ディレクトリがトップレベルに平置きされており、実装ディレクトリ (`core/` `analyzers/`) と視覚的に混在している

### 文章としての読みにくさ (2026-07-26 実測)

内容が正しくても、日本語として読み下しづらい記述が蓄積している。`design` / `context` / `adr` / `README` の本文 931 文を計測した結果は次のとおり。

- 平均文長は 64 文字で妥当だが、**140 文字を超える一文が 67 件 (7%)** あり、最長は 302 文字 (`design/features/graph/DesignDoc_graph.md:76`)。1 文に「担当の分離」「各担当の責務」「結果の受け渡し方」「判断の正本」「決定経緯」を詰め込んでおり、読点と括弧で節を継ぎ足す構造になっている
- **「正本」が 127 回**出現する。文書間の参照関係を表す語として多用されているが、日常語ではなく初見の読み手に伝わりにくい。「担保」9 回、「委譲」20 回も同様に硬い
- 強調 (`**`) と括弧書きの入れ子が多く、どこが主張でどこが補足か視覚的に判別しづらい

リポジトリには `styleguide-documents` skill があり「曖昧さを排除する」「後続作業できる粒度で書く」「人間が理解しやすい構造にする」「過剰な装飾を避ける」という原則が定義済みだが、既存文書がこれを満たしているかは点検されていない。

### コードコメントの言語の不統一

- Core (Go) は英語 795 行 / 日本語 0 行 (issue #34 で英語へ統一)
- Java Analyzer は日本語 約 1,900 行 / 英語 11 行
- `context/engineering.md` の Code Comment Boundary は「コード内コメントは英語で書く」とリポジトリ全体に読める書き方だが、Java Analyzer は日本語で運用されており**規約と実態が矛盾**している

設計文書・ADR・context が 3,195 行すべて日本語である以上、コードコメントも日本語へ揃えるほうが読み手の切り替えコストが小さい。Go の英語化はエコシステム慣習に沿った判断だったが、本リポジトリでは設計文書と同じ語彙で意味論を書けることを優先する。

## 想定ユーザー/ステークホルダー

- **リポジトリ開発者 (Fukuemon)**: 実装を再開するとき、README から現在地 (何が実装済みで何が残っているか) を把握したい。コードと設計文書を行き来する際に言語を切り替えたくない
- **AI エージェント (spec-\* workflow)**: 正本文書を読んで正しい配置・依存で実装したい。壊れたリンクや「未着手」の誤情報で判断を誤りたくない
- **将来のコントリビュータ**: 入口 (README) から必要な文書へ迷わず辿り着きたい

## 提供価値(成功条件)

- README を読めば**プロジェクトの現在地** (実装済みの範囲 / 進行中の issue / 未着手の Phase) が正確に分かる
- 文書内のリンクが**すべて解決する** (存在しないファイルへの参照がゼロ)
- 文書の**入口と層構造が 1 箇所で示され**、どの情報がどこにあるか読み手が判断できる
- 文書が**一読で意味を取れる**日本語で書かれている (長すぎる一文がなく、硬い専門語には説明があり、強調と補足が視覚的に区別できる)
- コードコメントの言語が**リポジトリ全体で日本語に統一**され、規約 (`context/engineering.md`) と実態が一致する
- 既存の外部挙動 (CLI / JSONL Protocol / 出力形式 / exit code) は一切変わらない

## スコープ

### やること

- **README の実態追随**: Status・doc map・ディレクトリ一覧・issue 進行表を現在の実装状況へ更新する。壊れたリンク (`context/project.md` 等) を修正する
- **文書構造の見直し**: 索引の分散、層とディレクトリの対応、`docs/` 新設の要否を検討し、再配置する。具体的な構造は設計フェーズで確定する
- **spec の closeout**: close 済み issue (#6 / #7 / #8 / #9 / #11 / #12 / #21 / #22 / #24 / #27) の spec を契約どおり削除する。参照の張り替えは issue #35 で完了済みのため、削除だけを行う
- **Go コードコメントの日本語化**: `core/` 配下の英語コメント 795 行を日本語へ変換する (package / 型 / 関数の doc comment と関数内の実装コメントの両方)
- **規約の改訂**: `context/engineering.md` の Code Comment Boundary を「コード内コメントは日本語で書く」へ改訂し、Java / Go の双方に一貫して適用する
- **文章の推敲**: 長すぎる一文の分割、硬い用語 (「正本」127 回など) の言い換えまたは用語集の整備、強調と括弧書きの整理を行う。基準は `styleguide-documents` skill の 5 原則に置く
- **文書のリンク検査**: 文書内リンクの解決を機械検査する仕組みを検討し、可能なら quality gate に組み込む

### やらないこと

- **コードの挙動変更**: リファクタリング・機能追加・アルゴリズム変更は行わない (コメントと文書のみ)
- **ユーザーに見える文字列リテラルの変更**: CLI 出力・エラーメッセージ・JSONL のフィールド値は観測可能な契約であり golden test が固定しているため変更しない
- **設計判断そのものの見直し**: ADR に記録済みの決定 (層構成 / ACL / 依存方向 / 外部ライブラリ隔離) は本 issue では再検討しない
- **推敲による内容の変更**: 読みやすさのための書き換えで、記述している判断・制約・契約の意味を変えない。意味を変える必要が見つかったら別 issue へ切り出す
- **sdd-template 側の変更**: 共有プロセス層 (`.rulesync/`) の改訂は対象外。テンプレ側の課題を見つけたら別 issue へ切り出す
- **PRD の新規作成**: 統合モード (Why/What は DesignDoc に内包) を維持する

## 監査/非機能要件

### 監査・運用

- 文書構造の変更判断 (docs/ 新設の要否、索引の集約先) は ADR または設計フェーズの決定として記録し、変更経緯を追跡可能にする
- spec の削除は git history に残るため、削除前に durable 側へ内容が移っていることを確認した記録を PR に残す

### 非機能(性能/可用性/セキュリティ/保守)

- **保守**: 新しい文書を追加するとき、置き場が一意に決まる程度に層の責務が明文化されていること
- **保守**: README が実態から再び乖離しないよう、更新のトリガー (どの変更のときに README を見直すか) を規約に定めること
- **セキュリティ**: 文書・コメントに secret / 認証情報 / 個人 PC の絶対パスを書かない (契約の既存規範)
- **互換**: 文書の移動でリポジトリ外から参照されている URL (GitHub の README リンク等) が壊れないこと

## 受け入れ基準 (EARS)

1. WHEN 開発者が README を読んだとき、THE SYSTEM SHALL 実装済みの範囲・進行中の issue・未着手の Phase を実態と一致した形で提示する。
2. THE SYSTEM SHALL リポジトリ内の文書から参照される相対リンクの参照先がすべて実在する状態を保つ。
3. THE SYSTEM SHALL `core/` および `analyzers/java/` のコード内コメントを日本語で記述し、`context/engineering.md` の Code Comment Boundary の記述と一致させる。
4. IF コメントの日本語化でユーザーに見える文字列リテラル (CLI 出力 / エラーメッセージ / JSONL の値) が変更された場合、THEN THE SYSTEM SHALL 既存の golden test / E2E で検出し CI を FAIL させる。
5. WHEN 再編成後に既存のテストスイート (Go unit / Java unit / E2E / golden / Gradle compatibility matrix) を実行したとき、THE SYSTEM SHALL テスト本体のロジック変更なしで全件 PASS する。
6. THE SYSTEM SHALL close 済み issue の spec ディレクトリを保持しない。
7. WHEN 新しい文書を追加しようとしたとき、THE SYSTEM SHALL 層の責務定義から置き場が一意に決まる状態を提供する。
8. THE SYSTEM SHALL 文書の本文に 140 文字を超える一文を持たない (表・コードブロック・引用を除く)。
9. WHERE 硬い専門語 (「正本」等) を用いる場合、THE SYSTEM SHALL その語の定義を用語集または初出箇所で示す。
10. IF 推敲によって記述している判断・制約・契約の意味が変わった場合、THEN THE SYSTEM SHALL その変更を推敲とは別の変更として切り出し、レビューで判別できる状態にする。
