# ADR-0009: framework 由来の暗黙の呼び出しを Protocol の schema を変えずに metadata で表し、receiver の型は型根拠を保つ救済層で導く

## Status

承認

## Context

変更の影響の調査は、edge が 1 本欠けると答えが間違う。  
それに対して、framework が実行時に起動する暗黙の呼び出しが edge にならない欠落が残っていた。  
実環境の検証用のプロジェクト（Gradle の multi-project、7 つの project、call site が 52,411 件）を測り、次の 5 つが分かった。

1. アノテーション駆動の entry point を、未解決と区別できない。
2. イベントの publish から listener への伝播が途切れる。
3. 値として渡した callable の invocation がつながらない。
4. 未解決の診断の約 91% が、stream と builder の連鎖と、generics の局所変数の receiver の型の導出の失敗である。
5. 既定の heap での `OutOfMemoryError` と、Gradle daemon の JVM の非互換が、解析の実行を妨げる。

この ADR は、これらを解くために比べて決めた判断の群を、1 本にまとめて記録する。  
関連する判断を個別の ADR に分けない前例は、次の 2 つ。

- SootUp の導入と Spring DI の解決を、1 つの feature として段階的に入れた。
  - ADR-0005: [Java Analyzer に SootUp による型階層の補完と Spring DI の解決を 1 つの feature として導入する](0005-adopt-sootup-and-spring-di-resolution.md)
- Core と Java Analyzer の依存境界に関する判断の群を、まとめて記録した。
  - ADR-0007: [Core と Java Analyzer の依存境界を ACL と機械のチェックで固定し、Core はフラットな package 構成のまま保つ](0007-layered-architecture-refactor.md)

前提にする決定は次のとおり。

- 動的な呼び出しの完全な追跡は見送っている。
  - ADR-0004: [動的呼び出しの完全追跡を初期スコープに含めず、候補と未解決理由を観測可能にする](0004-defer-runtime-call-tracing.md)
- source root は Gradle Tooling API で discovery する。
  - ADR-0006: [source root を指定しない request では、Gradle Tooling API で build の実効 model から解析 context を discovery する](0006-adopt-gradle-tooling-api-discovery.md)

## Decision

1. **Protocol の表現は、opaque な metadata と、新しい `JAVA_` の diagnostic code で閉じ、schema を変えない**。
2. **entry point の分類は edge を作らず、終端の根拠だけを付ける**。
   - 擬似の caller の node は合成せず、runtime-provided のマーカーの既存の設計を踏襲する。
3. **イベントの edge は、broadcast の意味論の専用の規則で表す**。
   - 合致した listener への edge は、複数でも、どれも確定（`resolution: unique`）にする。曖昧として扱うのは、条件つきの listener だけにする。
     - この判断のうち、曖昧として扱う listener の範囲は [ADR-0015](0015-ambiguous-generic-event-listeners.md) で置き換えた。
   - Spring DI の「複数の候補は曖昧」とは意味論が違うため、流用しない。
4. **callable の invocation の edge は、method reference なら参照先のメソッドへ、lambda なら定義した側の囲むメソッド（標識つき）へ張る**。
   - lambda の本体を独立した node にしない既存の決定を保ち、囲むメソッドへの edge を「invoker はそのメソッドの中で定義されたコードを実行する」の意味で使う。
   - 静的に追う範囲は、「同じメソッドの中」と「workspace のメソッドへの引数での受け渡しの 1 段」に限る。
5. **chain の型の解決は、型伝播の救済層で強める**。
   - solver が失敗したときに receiver の式の型を段階的に導き、既存の bytecode の救済へつなぐ。
   - SAM の arity も、functional interface の bytecode から導く。
   - 常に型根拠を保ち、宣言上の名前が一意であることだけを根拠にする救済は行わない。型根拠のない member の解決を採らないという既存の決定を守るためである。
6. **Console は、`entryPoint` の key に限って metadata を意味として解釈し、表示する**。
   - 「Output は metadata を意味として解釈しない」の唯一の例外にし、他の key の Console での表現は引き続き見送る。
7. **`OutOfMemoryError` は Core の側で検知し、対処を添えたエラーとして報告する**。
   - Analyzer が valid な `error` record を出さずに異常終了したときに限って stderr にヒントのパターンがあるかを調べ、解析の結果の解釈には使わない。
8. **Gradle daemon の JVM は、request の `metadata.gradleJavaHome` による明示の override だけを提供する**。
   - 互換のある JDK を暗黙に自動で探すことはしない。discovery を明示的に保つ方針を守るためである。

## Considered Options

### 暗黙の呼び出しの Protocol での表現（決定 1）

| 選択肢                                                              | 強み                                                                                  | 弱み                                                                                                                        |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **採用:** opaque な metadata と `JAVA_` の diagnostic code で閉じる | Protocol と Core の parser が変わらないため、他の言語の Analyzer への契約の影響がない | —                                                                                                                           |
| Protocol の schema を拡張する（新しい field、record）               | 言語によらない一級の表現になる                                                        | 契約の変更、Core の parser の改修、他の言語の Analyzer への負担が生じる。複数の言語の要求がない現時点では、過剰な設計である |

### イベントの edge の確度（決定 3）

| 選択肢                                                      | 強み                                                           | 弱み                                                                         |
| ----------------------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **採用:** broadcast の意味論の専用の規則にする              | 合致した listener への edge を、複数でもどれも確定として示せる | —                                                                            |
| DI の候補の規則を流用する（複数の listener は `ambiguous`） | 規則が単純                                                     | すべて実行される listener の群が「曖昧」と表示され、利用者が確度を読み違える |

### callable の invocation（決定 4）

| 選択肢                                                                                  | 強み                                          | 弱み                                                                                          |
| --------------------------------------------------------------------------------------- | --------------------------------------------- | --------------------------------------------------------------------------------------------- |
| **採用:** method reference は参照先へ、lambda は囲むメソッドへ標識つきで edge を張る    | callable を経由した暗黙の呼び出しを観測できる | lambda への invocation の edge は囲むメソッドの全体への近似で、粒度が粗い（標識で明示する）   |
| callable は diagnostic だけにする（edge を張らない）か、method reference だけに対応する | —                                             | 影響の伝播が途切れたままになり、callable を経由した呼び出しを edge として追う要求を満たさない |

### receiver の型の導出（決定 5）

| 選択肢                                                                     | 強み                                                                                                                | 弱み                                                                                             |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **採用:** 型根拠を保つ型伝播の救済層で導き、既存の bytecode の救済へつなぐ | 測って支配的だった未解決の形（receiver の型の導出の失敗、未解決の診断の約 91%）に、既存の bytecode の救済をつなげる | 導出の手段が増えるほど、解析のコストが増える（index を使って抑え、測って確かめる）               |
| 名前による救済を広げる（型根拠なしで bytecode の member を引く）           | —                                                                                                                   | 型根拠のない member の解決を採らないという既存の決定と正面から衝突し、誤った edge のリスクが高い |
| JavaParser の solver の本体の推論を補強する                                | —                                                                                                                   | 失敗する箇所が solver の内部に散らばり、副作用の範囲が読めない                                   |

### `OutOfMemoryError` の報告（決定 7）

| 選択肢                                       | 強み                                                                                     | 弱み                                                                                     |
| -------------------------------------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| **採用:** Core の側で検知する                | Analyzer が valid な `error` record を出さずに異常終了したときも、対処を添えて報告できる | —                                                                                        |
| Analyzer の側で OOM を `error` record にする | —                                                                                        | OOM の後の record の出力はメモリの確保を伴い、成功する保証がない（best effort に留まる） |

### Gradle daemon の JVM の選び方（決定 8）

| 選択肢                                                         | 強み                                 | 弱み                                                                                                                       |
| -------------------------------------------------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| **採用:** `metadata.gradleJavaHome` による明示の override だけ | discovery を明示的に保つ方針を守れる | —                                                                                                                          |
| 互換のある JDK を自動で探して代わりに使う                      | —                                    | 暗黙の JVM の選択は、利用者が信頼する build logic を利用者の権限で評価するという、discovery を明示的に保つ方針と相性が悪い |

## Consequences

### Positive

- entry point、イベント、callable の暗黙の呼び出しを観測でき、caller を探索したときの終端の根拠を示せる。
- 測って支配的だった未解決の形（receiver の型の導出の失敗、未解決の診断の約 91%）に、既存の bytecode の救済をつなげる。
- Protocol と Core の parser が変わらないため、他の言語の Analyzer への契約の影響がない。

### Negative

- lambda への invocation の edge は、囲むメソッドの全体への近似で、粒度が粗い。
  - 標識で明示する。
- Console が metadata を解釈しない契約に、例外が 1 つ入る。
  - 対象の key を `entryPoint` に固定して、広がるのを防ぐ。
- 型伝播の救済層の導出の手段が増えるほど、解析のコストが増える。
  - index を使って抑え、測って確かめる。
