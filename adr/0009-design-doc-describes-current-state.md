# ADR-0009: design doc には現在の設計だけを書き、決定の経緯は ADR に置く

## 状態

提案

## 決定日

2026-08-01 (起案)

> 状態が「提案」の間は起案日を記す。承認時に決定日へ置き換える。

## 背景

design doc (`design/DesignDoc.md` / `design/features/`) と context に、**現在の設計ではない情報**が蓄積している。実測 (2026-08-01):

| 対象                                                     | 実測                                              |
| -------------------------------------------------------- | ------------------------------------------------- |
| issue 参照                                               | design / context に 99 件 (`java-analyzer` が 32) |
| Phase 参照                                               | design 5 本                                       |
| `## メタ` / `## 上位資料からの変更点` / `## 変更履歴` 節 | feature doc 6 本すべてに 3 節とも存在             |

これらは「この issue で何を決めたか」「どう改訂してきたか」であって、**いま system がどうなっているか**ではない。読み手 (将来の開発者 / AI エージェント) が設計を知るために読むとき、経緯は雑音になる。

### 規約は既にあり、実態が追随していない

これは新しい方針ではない。`spec-contract.md` の正本境界は既にこう定めている。

> 判定の目安: 「issue が閉じても残り続ける設計情報」は design 正本、「この issue の意思決定の記録」は spec

`closeout.md` はさらに踏み込む。

> 選択肢を比較して決めた判断で ADR 未起票のものがあれば、削除前に ADR に起こす (spec 削除後、「なぜこうしたか」を再現できる場所は ADR だけになる)

つまり **spec に留めるべき経緯が design doc へ流れ込んでいる**のが現状であり、本 ADR はその適用を depwalk 側で明文化するものである。

### 直接の契機

[issue #40](https://github.com/Fukuemon/depwalk/issues/40) の frontmatter 移行で、ヘッダにあった改訂注記 (最長 300 字) を `## 変更履歴` 節へ移した。これは移し先の誤りだった。経緯は ADR と git history にあれば足り、`verified_commit` を導入した今、design doc が改訂履歴を持つ理由はない。

## 決定

### 1. design doc は現在の設計だけを書く

design doc / feature doc / context は「いま system がどう設計されているか」だけを保持する。過去にどうだったか、なぜ変えたかは書かない。

### 2. 経緯の置き場

| 情報                                 | 置き場                             |
| ------------------------------------ | ---------------------------------- |
| 選択肢を比較して決めた判断とその理由 | ADR                                |
| 改訂の日付・順序                     | git history (`git log -- <doc>`)   |
| 作業単位の議論                       | issue / PR                         |
| 現在の設計・契約・制約               | design doc / feature doc / context |

**「なぜこうしたか」を design doc に書きたくなったら、それは ADR にすべき判断である。** design doc からは `(判断の正本は ADR-XXXX)` の形で 1 行参照する。

### 3. 廃止する節

feature doc から次の 3 節を廃止する。

| 節                        | 廃止理由                                                                                                   |
| ------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `## メタ`                 | 「関連 issue」は経緯。「対象モジュール」は frontmatter の `governs` と重複。他の行は inline リンクで足りる |
| `## 上位資料からの変更点` | 「この issue が上位文書へ何を反映したか」= spec 時点の作業記録であり、design doc に来る理由がない          |
| `## 変更履歴`             | 改訂の経緯。git history と ADR で足りる                                                                    |

ADR への参照は節にまとめず、**その判断を説明している箇所へ inline で置く**。読み手が「なぜ」を知りたくなる場所と参照が同じ位置にあるほうが辿りやすい。

### 4. issue 参照は原則書かない

例外は 1 つだけ: **未解決の論点**を指す場合。「この点は #NN で検討中」は現在の状態を語っており、解決したら記述ごと消える。

解決済みの決定を指す issue 参照は、対応する ADR への参照に置き換えるか、削除する。

### 5. Phase 参照は DesignDoc に集約する

「Phase N で実装する」はロードマップであり、feature doc が持つと更新漏れで腐る。ロードマップの正本は `design/DesignDoc.md` とする。

ただし**実装状況そのものは現在の事実**なので feature doc に書いてよい。「DOT / Mermaid は未実装」は書く。「Phase4 で実装」は書かない。

## 代替案

### 却下: 規約化せず推敲の中で黙って直す

文書は減るが、後から「経緯を書き戻したい」提案が来たときに根拠が残らない。99 件の削除は一度きりの作業ではなく、今後も同じ判断を繰り返すため、判断の正本が要る。

### 却下: 経緯を design doc に残したまま、節を整理するだけ

読み手が設計を知るために読む文書に経緯が混ざる問題は解けない。`java-analyzer` の 32 件のような密度では、設計の記述より経緯のほうが目に入る。

### 却下: ADR 化せず一律削除する

最も速いが、ADR になっていない決定を消すと「なぜこうしたか」が完全に失われる。`closeout.md` が禁じている操作そのものである。削除前に 1 件ずつ「既存 ADR へのリンクに置換 / 新規 ADR を起こす / 単に消す」を判定する。

## 影響

### 良い影響

- design doc が「いま何がどう設計されているか」だけになり、読む量が減る
- 「なぜ」を探す場所が ADR に一本化され、探索先が一意になる
- feature doc の 3 節が消え、テンプレートから起こす新規文書も最初から軽い

### 悪い影響 / トレードオフ

- 99 件の issue 参照を 1 件ずつ判定する必要がある。機械的な一括削除にはできない
- ADR が増える。ただし「選択肢を比較した判断は ADR」は既存の規約であり、本 ADR で増えるのは記録漏れの回収分である
- 経緯を追うのに git history を辿る手間が増える。`verified_commit` が commit を指すため起点は得られる

### 影響範囲

- 対象モジュール / package: 横断 (`domain:core`)。実装コードへの変更はなく、対象は `design/` / `context/` / `templates/` / `adr/`

## 実装・運用への反映

- spec 更新要否: 要。[issue #40](https://github.com/Fukuemon/depwalk/issues/40) の推敲スコープへ「経緯の除去と ADR 化」を追加する
- 適用の順序: `templates/features/template.md` から 3 節を外し、既存 6 本は `verified_commit` 消し込みのバッチ作業と同時に処理する (どちらも文書を 1 本ずつ精読する作業であり、分けると二度読みになる)
- context / AI 向け設定更新要否: 否。規約自体は `spec-contract.md` の正本境界に既にあり、本 ADR はその適用を定めるもの
