# ADR-0011: 文書は平置きのまま置き、読みやすさは機械検査と言い換えで担う

## 状態

提案

## 決定日

2026-08-02 (起案)

> 状態が「提案」の間は起案日を記す。承認時に決定日へ置き換える。

## 背景

[issue #40](https://github.com/Fukuemon/depwalk/issues/40) は「文書が実態とずれている」「読み下しづらい」の 2 つを課題として起票した。前者は [ADR-0008](0008-doc-freshness-and-reading-map.md) の `governs` / `verified_commit` と読み取りマップの生成で解いた。後者について、要求フェーズで挙がった 4 つの論点が未決のまま残っている。

| 論点 | 内容                                                             |
| ---- | ---------------------------------------------------------------- |
| 1    | `docs/` を新設して design / context / adr を集約するか、平置きか |
| 4    | 文書リンクの機械検査を導入するか                                 |
| 6    | 硬い用語 (「正本」など) を言い換えるか、用語集を作って残すか     |
| 7    | 一文の長さや用語を機械検査するか                                 |

いずれも「どちらでも動く」種類の選択であり、決めずに進むと次に文書を触る人が毎回考え直すことになる。

作業を通じて分かった事実が 2 つある。

- **切れリンクは実際に発生していた**。#40 の作業中に手元のスクリプトで追跡ファイルの相対リンク 388 件を検査したところ、切れが 2 件見つかった。うち 1 件は ADR-0008 が自ら改名した `context/impact-index.yaml` を指したままで、改名した本人が気づいていない
- **長い一文は構造の中に残っていた**。2026-07-26 の実測では 140 文字超が 67 件あり、推敲で本文からはほぼ消えた。ただし表・箇条書きの中には残っており、目視では見落とす

## 決定

### 1. 平置きを維持する (論点 1)

`design/` `context/` `adr/` `specs/` `templates/` はリポジトリ直下に置いたままにする。`docs/` を新設して集約しない。

### 2. リンク検査を CI へ入れる (論点 4)

追跡ファイルの相対リンクを検査する `scripts/check-links.py` を置き、Docs job で実行する。切れリンクは FAIL とする。

コードフェンスとコードスパンの中は検査しない。索引の出力例のように、リンクの**書式**を示すために書かれたものを切れリンクとして数えないため。

`templates/` は検査対象から外す。テンプレ内のリンクはテンプレの**配置先** (`context/architecture.md` など) からの相対 path であり、テンプレ自身の位置からは解決しないためである。

### 3. 一文の長さを textlint で検査する (論点 7)

`textlint` + `textlint-rule-sentence-length` (max 140) を Docs job で実行する。`textlint-filter-rule-node-types` で `BlockQuote` / `ListItem` / `Table` / `CodeBlock` / `Code` / `Html` を除外する。

除外するのは、表の 1 セルや箇条書きの 1 項目を 140 文字に収めるために内容を削ると、かえって情報が落ちるためである。散文を読み下せる長さに保つのが目的であり、構造化して並べたものはその対象外とする。

### 4. 硬い用語は言い換える (論点 6)

「正本」164 回、「委譲」22 回、「担保」16 回を平易な表現へ置き換える。用語集に定義を足して残す案は採らない。

用語集は**このプロダクト固有の語** (`Analyzer` / `Traversal Engine` など) を定義する場所であり、日本語の言い回しの硬さは用語集で解決する問題ではない。読み手が索引を引かないと読めない文書は、索引があっても読みにくい。

## 代替案

### `docs/` を新設して集約する (論点 1)

トップレベルに実装ディレクトリ (`core/` `analyzers/`) と文書ディレクトリが混在する見た目は解消する。

採らない理由は 2 つある。1 つは sdd-template との差分が広がること。skill とテンプレは `design/` `context/` `adr/` `specs/` を repo ルート直下と決め打ちで参照しており、集約すると全 skill の path を書き換えたうえでテンプレ側にも反映する必要がある。もう 1 つは、混在の解消が「読みやすさ」に効く度合いが小さいこと。読み手が最初に困るのは「どこから読むか」であり、それは [ADR-0008](0008-doc-freshness-and-reading-map.md) の読み取りマップで解いている。

### 機械検査を入れず人手レビューに留める (論点 4 / 7)

導入コストはゼロになる。

採らない理由は、#40 の作業中に両方とも**人手で見落とした実例が出た**ことにある。改名した本人がその改名先へのリンクを直し忘れ、推敲を通した文書に 140 文字超が残っていた。人手で気づけるなら既に気づいていたはずのものである。

### textlint に技術文書向けプリセットをまとめて入れる

`textlint-rule-preset-ja-technical-writing` は一文の長さのほかに、である調の混在・二重否定・読点の数など十数個の規則を持つ。

採らない理由は、既存文書に対する違反が多く、規則ごとに「直す / 無効にする」の判断を迫られること。今回入れたいのは #40 の受け入れ基準 8 に対応する一文の長さだけであり、規則を絞ったほうが検査の意味が明確になる。必要になった時点で 1 つずつ足す。

### 硬い用語を用語集に定義して残す (論点 6)

202 箇所の書き換えが不要になる。

採らない理由は、用語集の役割が変わってしまうこと。`context/project.yml` の `glossary` は「このプロダクトを知らない人が読めないドメイン語」を定義する場所である。そこに一般的な日本語の硬い言い回しを足すと、何をドメイン語として管理しているのかが曖昧になる。

## 影響

- Docs job に検査が 2 つ増える。textlint は `npx` の pinned 実行で `node_modules` を作らない (prettier と同じ扱い。`hooks/format/run_prettier.sh` を踏襲する)
- 言い換えは 202 箇所に及び、文書の意味を変えずに置換できたかのレビューが要る。推敲とは別の変更として切り出す (#40 の受け入れ基準 10)
- textlint の除外設定により、表・箇条書きの中の長文は検査されない。ここは引き続き書き手の判断に委ねる

## 実装・運用への反映

- `scripts/check-links.py` / `.textlintrc.json` を追加し、`.github/workflows/ci.yml` の Docs job から実行する
- 検出された 10 件の長文を分割する
- 「正本」「委譲」「担保」の言い換えは別 PR で行う
- pre-commit へは入れない。文書 1 本の編集で repo 全体を検査することになり、commit の待ち時間に見合わない
