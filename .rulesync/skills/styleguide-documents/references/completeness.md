# 漏れを防ぐ：境界、異常系、影響、検証

正常系だけで終わらせず、境界、異常系、影響、検証可能性を書ききるための作法。

## 目次

- 境界を書く
- 異常系を書く
- 影響を書く
- 検証可能に書く

## 境界を書く

docs では、境界を明確にする。
境界が曖昧な文書は、実装、レビュー、運用で解釈が割れる。

境界として書くべきものには、次がある。

- 対象範囲と非対象。
- 責務の分界。
- 入力と出力。
- 正常系と異常系。
- ユーザー操作とシステム処理。
- 同期処理と非同期処理。
- 永続データと一時データ。
- 手動対応と自動処理。
- 現時点で決めることと後で決めること。
- 正本となる文書と参照先の文書。
- 上位文書と下位文書の責務。

悪い例：

通知送信は別処理で行う。

良い例：

通知レコードの作成はアプリケーション側で行う。
外部チャネルへの配信は、通知レコード作成後に非同期ジョブで行う。
配信ジョブの失敗は通知レコードの作成結果には影響させない。

## 異常系を書く

正常系だけを書かない。
異常系、境界値、部分失敗、再試行、復旧方法を書く。

悪い例：

送信に失敗した場合はリトライする。

良い例：

外部サービスが 5xx を返した場合は、最大 3 回まで指数バックオフで再試行する。
4xx の場合は再試行しない。
3 回失敗した場合は failed 状態として保存し、運用者向けのアラートを送る。

異常系では、次を明確にする。

- 何が失敗とみなされるか。
- 失敗時に利用者へ何を返すか。
- 失敗時に内部状態をどう更新するか。
- 再試行するか。
- 再試行しない条件は何か。
- 復旧は自動か手動か。
- 何をログに残すか。
- どの条件で通知するか。

## 影響を書く

変更や判断には影響がある。
影響を書かないと、読み手はリスクを判断できない。

影響として確認するものには、次がある。

- 利用者への影響。
- 既存機能への影響。
- データへの影響。
- 運用への影響。
- 監視への影響。
- セキュリティへの影響。
- コストへの影響。
- パフォーマンスへの影響。
- リリース作業への影響。
- ロールバックへの影響。
- 関連 docs への影響。

影響がない場合も、確認したうえで「影響なし」と書く。
確認していないものを「影響なし」と書かない。

## 検証可能に書く

抽象的な品質は、できるだけ観測可能な形にする。

悪い例：

高速に表示する。

良い例：

一覧取得は 20 件ずつページングする。
1 ユーザーあたり 1,000 件のデータがある状態で、p95 300ms 以下を目標とする。

悪い例：

安全に処理する。

良い例：

認証ユーザーの user_id と対象データの user_id が一致する場合だけ取得を許可する。
一致しない場合は 404 を返し、対象データの存在有無を推測できないようにする。

測定できない場合は、測定できない理由を書く。
そのうえで、代替となる観測指標を書く。
