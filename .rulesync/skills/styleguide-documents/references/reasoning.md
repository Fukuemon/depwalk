# 判断と根拠の書き方

事実と判断の区別、要求と実現方法の分離、判断理由、比較、制約、前提、未決事項の扱い。

## 目次

- 事実、判断、仮定を分ける
- 要求と実現方法を混ぜない
- 判断理由を書く
- 比較を書く
- 制約を書く
- 前提と未確認事項
- 未決事項を書く

## 事実、判断、仮定を分ける

docs では、事実、判断、仮定を混ぜない。

**事実**は、確認済みの情報である。
**判断**は、事実や制約をもとに選んだ方針である。
**仮定**は、現時点では成り立つものとして扱う条件である。

悪い例：

既存 DB にユーザー情報があるので、通知も同じ DB に置くのが自然である。

良い例：

既存 DB にはユーザー情報が保存されている。
通知はユーザー ID と紐づけて取得する必要がある。
そのため、通知履歴は既存 DB に保存する方針とする。

「自然」「妥当」「適切」のような評価語だけで判断を済ませない。
何に基づいてそう判断したのかを書く。

## 要求と実現方法を混ぜない

要求は「満たすべきこと」を書く。
実現方法は「どう満たすか」を書く。

悪い例：

通知は PostgreSQL の notifications テーブルに保存する必要がある。

この文は、要求と実現方法を混ぜている。

要求として書くなら、次のように書く。

ユーザーは、自分宛ての通知履歴を取得できる必要がある。
通知履歴は永続化する必要がある。

実現方法として書くなら、次のように書く。

通知履歴は PostgreSQL の notifications テーブルに保存する。
既存のユーザーデータが PostgreSQL にあり、通知の取得でもユーザー ID による参照整合性が必要になるためである。

## 判断理由を書く

何かを選ぶときは、選んだ結論だけで終わらせない。
判断理由と影響を書く。

悪い例：

今回は PostgreSQL を使う。

良い例：

通知履歴の保存先には PostgreSQL を使う。
通知はユーザー ID と強く紐づき、既読状態の更新でもトランザクションが必要になる。
既存のユーザーデータも PostgreSQL にあるため、通知履歴を同じ DB に置くと参照整合性を扱いやすい。

この方針では、通知履歴の取得が既存 DB の負荷に影響する。
通知件数が増える場合は、ユーザー ID と作成日時の複合インデックスを前提にする。

判断を書くときは、最低限次を含める。

- 何を選んだか。
- なぜその選択をしたか。
- どの制約に基づく判断か。
- 何が簡単になるか。
- 何が難しくなるか。
- どの条件で見直すか。

## 比較を書く

比較は、採用した案を正当化するための飾りにしない。
実際に選べる選択肢だけを書く。

比較を書くときは、同じ観点で並べる。

悪い例：

Redis は永続化に向かないので採用しない。

良い例：

Redis を主たる保存先にする案も検討した。
通知取得の低レイテンシ化はしやすい。
一方で、通知履歴はユーザーが後から参照するデータであり、既読状態の永続化と復旧時の扱いが問題になる。
今回の要求では履歴の保持が必要なため、Redis を主たる保存先にはしない。
将来、未読件数のキャッシュが必要になった場合は、永続データを別に持ったうえで Redis を派生データとして使う余地がある。

比較には、次を含める。

- 選択肢の概要。
- その選択肢で簡単になること。
- その選択肢で難しくなること。
- 今回選ばない理由。
- 将来選びうる条件。

## 制約を書く

制約は、判断に影響するものだけを書く。
文書に出した制約は、後続の判断で回収する。

制約には、たとえば次の種類がある。

- 技術的な制約。
- 運用上の制約。
- 組織上の制約。
- セキュリティ上の制約。
- 法務上の制約。
- 性能上の制約。
- 期限上の制約。
- 予算上の制約。

制約を単なる前置きで終わらせない。
判断理由として使わない制約は、文書から外すか、補足に下げる。

悪い例：

既存システムでは PostgreSQL を使っている。
今回は PostgreSQL を使う。

良い例：

既存システムでは PostgreSQL を使っている。
通知は既存ユーザーと紐づくため、同じ DB に保存すると参照整合性を保ちやすい。
そのため、通知履歴の保存先には PostgreSQL を使う。

## 前提と未確認事項

前提と未確認事項を混ぜない。

**前提**は、文書内の判断が成り立つために置く条件である。
**未確認事項**は、まだ確認できていない事実である。

悪い例：

通知件数はそこまで多くない想定。

良い例：

前提として、通知件数は 1 ユーザーあたり月 1,000 件以下とする。
この値は現行ログから確認する必要がある。

未確認事項には、確認方法、担当、期限、判断への影響を書く。

- **未確認事項**：月間通知件数の上限。
- **確認方法**：直近 3 か月のイベントログから通知候補数を集計する。
- **担当**：バックエンド担当。
- **期限**：実装開始前。
- **影響**：件数が想定を超える場合、保存期間とインデックス設計を見直す。

## 未決事項を書く

未決事項は、TBD とだけ書かない。
未決であること自体も、文書内で管理できる状態にする。

悪い例：

通知の保存期間は TBD。

良い例：

通知の保存期間は未決定である。
候補は 90 日、180 日、無期限の三つである。
保存期間は DB 容量、問い合わせ対応、監査要件に影響する。
履歴参照期間の要求を確認してから決定する。

未決事項には、次を含める。

- 何が未決定か。
- どの選択肢があるか。
- 何に影響するか。
- 誰が決めるか。
- いつまでに決めるか。
- 決定に必要な情報は何か。
