## 整形

- 原則として一文ごとに改行する。
- 段落の区切りは空行で示す。
- 一つの段落には一つの論点だけを置く。
- コード、ログ、SQL、設定、差分、コマンド例はコードブロックで示す。
- 表は、比較、対応関係、状態一覧、責務分担、条件整理に使う。
- 箇条書きは、条件、制約、要求、非対象、未決事項、確認事項に使う。
- 箇条書きだけで論証を済ませない。
- 箇条書きの前に、その一覧が何を表すのかを一文で置く。
- 用語を初めて導入するときは太字にする。
- 以後の言及、引用、通称には「」を使う。
- 用語と定義を並べるときは、全角コロンで「**用語**：説明」と書く。
- ダッシュ類を日本語の地の文・見出しで使わない。
- 中黒を日本語の並列で使わない。
- 見出しに区切り線で複数の要素を詰め込まない。
- 見出しは、その節が扱う対象か問いを具体的に示す。

## 用語を管理する

同じ対象には同じ名前を使う。
一つの文書内で「通知」「メッセージ」「お知らせ」を混在させない。

画面上の表記、コード上の名前、文書内の用語が違う場合は、対応表を置く。

| 文書内の用語 | 画面上の表記 | コード上の名前 | 説明                           |
| ------------ | ------------ | -------------- | ------------------------------ |
| 通知         | お知らせ     | notification   | ユーザーに表示するアプリ内通知 |

用語を新しく作るときは、既存の慣用語を優先する。
一般的な技術用語を、独自の意味で使わない。
独自の意味で使う必要がある場合は、初出で定義する。

## 論証を一方向に進める

段落は論証の一歩として書く。
一つの段落に複数の論点を混ぜない。

- 段落の最初の文で、その段落の話題を示す。
- 前の段落との関係を接続表現で示す。
- 結論を出してから反論を処理し、また結論を言い直す構成にしない。
- 疑念や反論を処理してから、結論を一度だけ置く。
- 否定するときは、否定する命題を正確に書く。
- 「A ではなく B」と書くときは、なぜ A ではないのかを添える。
- 因果を主張するときは、なぜそうなるのかを書く。

悪い例：

この構成は疎結合である。

良い例：

この構成では、通知生成と配信処理を別の責務として分ける。
通知生成は配信チャネルを知らず、配信処理は保存済みの通知レコードだけを読む。
そのため、配信チャネルを追加しても通知生成の処理を変更しなくてよい。

## 読み手の負荷を下げる

読者の記憶と注意は有限の資源として扱う。

- 後で参照しない固有名を出さない。
- 詳細名が必要な場合は、先に役割を説明してから名前を出す。
- 抽象語が指す内容を、その場で特定する。
- 似た概念は表で比較する。
- 状態遷移は文章だけで説明せず、表または図で示す。
- 複雑な処理順序は、手順番号を使う。
- 長い箇条書きは、分類して分ける。
- 読者に前の節を読み返させる参照を減らす。
- 文書間で同じ情報を重複させない。

悪い例：

この場合、前述の処理を使う。

良い例：

この場合、通知生成時に保存した delivery_status を参照する。

## 曖昧表現を避ける

中身のない表現で判断を隠さない。

次の表現は、具体的な情報を足さない限り使わない。

- 適切に。
- 必要に応じて。
- 可能な限り。
- 柔軟に。
- スケーラブルに。
- 保守性を高める。
- 責務を明確にする。
- 疎結合にする。
- 将来の拡張を見据える。
- ベストプラクティスに従う。
- セキュリティを考慮する。
- パフォーマンスに配慮する。
- TBD。
- 別途検討。
- 詳細は後で詰める。

これらの表現を使いたくなったら、条件、対象、手段、判断基準に置き換える。

悪い例：

必要に応じてリトライする。

良い例：

外部 API が 5xx を返した場合は、最大 3 回まで指数バックオフで再試行する。
4xx の場合は再試行しない。

悪い例：

責務を明確にする。

良い例：

通知生成は application service が担う。
配信チャネルごとの差分は adapter が担う。

## LLM っぽい表現を避ける

中身のない型で文書を埋めない。

次のような表現は、論点を増やさずに文章だけを膨らませやすい。

- 重要なのは。
- 鍵となる。
- 不可欠。
- 核心的。
- 多角的に。
- 包括的に。
- 深掘りする。
- 正面から扱う。
- 見ていく。
- まとめると。
- 要するに。
- と言えるだろう。
- ではないだろうか。

推量、仮定、未確認事項、読み手の疑念を表す場合は、弱い述語を残してよい。
根拠なく主張を弱めているだけなら削る。

悪い例：

この構成は、将来の拡張を見据えた柔軟な設計と言えるだろう。

良い例：

この構成では、通知チャネルごとの処理を adapter に閉じ込める。
そのため、メール通知を追加するときは、通知生成の共通処理を変えずに adapter を追加できる。

## 冗長を削る

docs では、同じ主張を繰り返さない。
読み手は、文芸的な反復ではなく判断材料を求めている。

- 冒頭で述べた目的を各節で言い直さない。
- 判断理由を複数の節で重複させない。
- 直前の内容を言い換えるだけの要約を置かない。
- 「これは重要である」のような評価文を置かない。
- 判断に使わない歴史的経緯を書かない。
- 比較表に書いた内容を本文で全項目なぞらない。
- 接続や評価のためだけの文を置かない。
- 読者が自力で補える中間説明を省く。
- 判断に必要な情報だけを残す。

## 書き換え例

悪い例：

エラー時は適切に処理する。

良い例：

入力値が不正な場合は 400 を返す。
認証されていない場合は 401 を返す。
認証済みだが対象リソースへの権限がない場合は 404 を返す。

悪い例：

将来的な拡張に対応できるようにする。

良い例：

通知チャネルは interface として定義し、メール、プッシュ、アプリ内通知を adapter として追加できる構成にする。

悪い例：

パフォーマンスに配慮する。

良い例：

一覧取得は作成日時の降順で 20 件ずつ取得する。
user_id と created_at の複合インデックスを作成し、全件走査を避ける。

悪い例：

セキュリティを考慮する。

良い例：

認証ユーザーの user_id と対象データの user_id が一致する場合だけ取得を許可する。
一致しない場合は 404 を返す。
