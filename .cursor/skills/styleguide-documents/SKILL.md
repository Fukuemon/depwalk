# Styleguide: Documents

技術的な docs を書くときの再利用可能な原則層。

この skill は、特定の文書フォーマットを定めるものではない。
文書種別ごとの見出し構成、記入例、テンプレートは別の skill や template が担う。
この skill には、プロジェクトや文書種別をまたいで流用できる「書き方の原則」だけを置く。

docs の目的は、読み手に情報を渡すことだけではない。
読み手が、理解、判断、実装、レビュー、運用、保守のいずれかの行動を取れる状態にすることである。

この SKILL.md は原則と索引を担い、具体例つきの詳細は `references/` に置く。
判断に迷ったら、5 原則と基本方針を満たしているかを先に確認し、該当トピックの reference を開く。

> **読み物系の文章を書くときの必読**: 記事 / 解説 / 章立ての文章など「読み物として読ませる」文章を
> 生成・推敲する場合は、`references/prose-rhythm.md` (緩急・認知リズムの規範) を必ず読む。
> spec / ADR / context などの技術文書には適用しない (5 原則の曖昧さの排除と衝突するため)。

## いつ使うか

この skill は、次の場面で使う。

- 技術的な docs を新規作成するとき。
- 既存 docs を更新するとき。
- 既存 docs が、後続作業に使える粒度か確認するとき。
- 文書をどの単位で分割するか判断するとき。
- 文書内の曖昧さ、重複、未決事項、境界の漏れを点検するとき。
- 人間または AI が、追加質問なしに次の作業へ進める状態へ整えるとき。
- 読み物として読ませる文章 (記事 / 解説 / 章立ての文章) を生成・推敲するとき (→ `references/prose-rhythm.md` 必読)。

## 5 原則

### 曖昧さを排除する

主語、対象、条件、判断基準を明示する。

「適切に」「必要に応じて」「柔軟に」「いい感じに」のような解釈余地のある語は、条件、閾値、具体例、責務、判断基準に置き換える。

悪い例：

必要に応じてリトライする。

良い例：

外部 API が 5xx を返した場合は、最大 3 回まで指数バックオフで再試行する。
4xx の場合は再試行しない。

### 意思決定理由を残す

「何を決めたか」だけでなく、「なぜそう決めたか」「どの制約に基づいたか」「どの選択肢を選ばなかったか」を残す。

判断理由を書かない docs は、将来の変更時に再利用しにくい。
読み手は、結論だけでなく、その結論がどの条件で成り立つのかを知る必要がある。

### 後続作業できる粒度で書く

docs は、読み物ではなく作業の入力である。

入出力、境界、受け入れ基準、異常系、未決事項を、実装者やレビュアーが追加質問なしに次の作業へ進める粒度で書く。

曖昧さが残る場合は、本文で滑らかにごまかさない。
未決事項として、選択肢、影響、確認方法、担当、期限を明示する。

### 人間が理解しやすい構造にする

読み手の認知負荷を下げる。

見出し、段落、表、箇条書き、図を使い、1 節 1 主題に保つ。
文書全体は、背景、対象、判断、実現方法、影響の順に流れるようにする。

同じ情報を複数箇所に複製しない。
正本がある情報は、要約とリンクにとどめる。

### 過剰な装飾を避ける

意味を持たない強調、絵文字、冗長な前置き、空虚な総括を使わない (初出用語の太字は `references/writing-style.md` の整形規則に従う)。

情報密度を優先する。
「重要なのは」「鍵となる」「包括的に」「深掘りする」のような表現で、具体的な情報の不足を補ったように見せない。

## 基本方針

- docs は、作業の入力として書く。
- 読み手が次に何を判断・実行すればよいかを明確にする。
- 事実、判断、仮定、未確認事項、未決事項を分けて書く。
- 背景、目的、制約、判断理由、影響を残す。
- 後から検証できる粒度で書く。
- 読み手が誤読しそうな箇所は、先回りして限定する。
- 文章の滑らかさより、解釈の一貫性を優先する。
- 「読めば何となく分かる文」ではなく、「レビューで指摘できる文」にする。
- 文書内で出した制約、前提、未決事項は、後続の判断や点検項目で回収する。

## 停止条件

次の状態では、文書を確定させない。

- 曖昧さを解消できる情報が不足している。
- 主要な判断の根拠が書けない。
- 対象範囲と非対象を分けられない。
- 未決事項の影響が分からない。
- 読み手に求める行動が定まらない。
- 正本となる情報源が分からない。
- 文書の粒度が大きすぎて、読者や目的が混在している。
- 図表が推測に基づいている。
- 後続作業に必要な入力、出力、境界、受け入れ基準が書けない。

情報が不足している場合は、本文を滑らかに補完しない。
ユーザーに確認するか、未決事項として記録する。
