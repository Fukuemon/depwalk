# Phase: prompts (tasks)

完成済 spec から、後続の実装セッションが自己完結に実行できる Markdown prompt を `specs/<...>/prompts/` 配下に生成する phase。

目次: 絶対ガード / 生成モード判定 / 先に読むもの / 出力先・命名規則 / 手順 / 生成後の報告 / 停止条件

## 絶対ガード (違反時は生成を中止してやり直し)

生成した **すべての prompt** に以下が揃っていること。
1 つでも欠けていたらその prompt は未完成。書き直す。

| #   | 必須セクション          | 省略不可の理由                                                                                                                               |
| --- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 0   | 先頭 frontmatter        | 機械可読な実行契約 (`phase` / `seq` / `target` / `issue` / `depends_on`)。後段のツール・実行者が本文を読まずに実行順・対象・実依存を解決する |
| 1   | `## 絶対ルール`         | 探索禁止 / 不明点ハンドリング / 別 prompt 領域への侵入禁止 / `antipatterns.md` の制約ブロック                                                |
| 2   | `## 作業ステップ`       | 各ステップに検証手順を含む                                                                                                                   |
| 3   | `## 実装コンテキスト`   | spec / 関連 path / 必要な前提を列挙                                                                                                          |
| 4   | `## 前提条件`           | 依存先 prompt / 必要な repo 状態                                                                                                             |
| 5   | `## 不明点ハンドリング` | 矛盾 / 欠落時に停止して確認する指示                                                                                                          |
| 6   | `## タスク境界`         | 実装する範囲 / しない範囲                                                                                                                    |
| 7   | `## 設計仕様`           | spec 該当節を必要最小限で抜粋                                                                                                                |
| 8   | `## テスト観点`         | 該当 spec のテスト観点を抜粋                                                                                                                 |
| 9   | `## 検証コマンド`       | repo の標準 task (build / lint / typecheck / test / e2e)                                                                                     |
| 10  | `## 完了条件`           | チェックリスト形式。実行者は最初にこれをタスク化する                                                                                         |

## 生成モード判定 (新規実装 / 差分修正)

生成の最初に、本設計が **新規実装** か **既存実装の差分修正** かを判定する。
判定軸は「**変更対象の既存実装コードが在るか**」(scaffold の「実装突合: 対象」フラグは突合要否の印であって、実装方式の印ではない):

- **差分修正モード**: 変更先の既存実装コードが存在し、spec の差分・論点が既存ファイルの変更を指す
- **新規実装モード** (既定): ゼロからの新規機能。未実装なら共有挙動を参照する場合でも新規実装
- 判定が付かなければユーザーに確認する (推測で決めない)。結果を spec の `## 設計フェーズ状況` 備考に「prompts: 差分修正モード / 新規実装モード」と明記する

**差分修正モードの生成規則** (既存ファイルの二重実装や migration の再作成を防ぐ):

- 対象は spec の `## 上位資料からの変更点` + 今回の論点が指す差分だけ。機能全体を再実装しない
- 変更先の既存ファイルを spec の差分が名指しするパスから特定して prompt に列挙する (探索禁止は維持)
- `## タスク境界` の「実装しない範囲」に「新規機能の作成 / 既存 migration の再作成 / 無関係な既存挙動」を明記する。スキーマ追加が要る場合のみ追加 migration (次番号) を作る
- `## 作業ステップ` は「既存ファイルを Read → 該当箇所を Edit → 既存テスト更新 + 差分の新規テスト → レビュー」の修正フローにする (新規雛形生成ステップを出さない)
- prompt 本数は差分の規模に合わせる (層ごとの機械分割をしない)
- 再発防止の観点 (再現条件 → 修正後の期待) を `## テスト観点` に必ず含める

## 先に読むもの

- `spec-contract.md` (Spec Workflow Contract)
- `prompt-rules.md` (同 dir) — 分割 / 命名 / 自己完結性のルール
- `prompt-template.md` (同 dir) — prompt 本体テンプレート
- `antipatterns.md` (同 dir) — 生成 prompt の `## 絶対ルール` に注入する実装制約
- 対象 spec の `index.md` 全体

## 出力先

```text
specs/<...>/prompts/
├── P1_01_*.md    # phase 1: 並列不可の基盤作業
├── P2_01_*.md    # phase 2: P1 完了後
└── ...
```

## 命名規則

```text
P{phase}_{seq}_{target}_{scope}.md
```

- `phase`: 実装 phase (1 始まり)
- `seq`: phase 内連番 (2 桁ゼロ埋め)
- `target`: `context/project.yml` の対象ドメイン一覧から選ぶ
- `scope`: 1 prompt で扱う責務 (ケバブケース)

例 (target はプロジェクトの対象ドメインに置き換える):

- `P1_01_<target>_page_shell.md`
- `P1_02_<target>_component_variants.md`
- `P2_01_<target>_flow.md`

## 手順

1. **生成モード判定** (上記): 差分修正モードなら以降の分割・タスク境界・作業ステップを差分修正規則に従わせる
2. spec の `未確定事項` がゼロであることを確認 (1 件でも残れば停止)
3. 直前 gate (既定列では track) のレビューが PASS であることを確認 (なければ `spec-review` を先に呼ぶ。prompts 自体のレビューは本 phase 完了後の最終 gate)
4. **最終検知ガード**: spec 全体を読み「要求 / 設計段階で書かれているべきだったが漏れている」内容がないかを確認する
   (設計完了直前の最後の検出点)。検知したら `workflow-git` の `references/derived-issue.md` に従い停止して
   派生 issue を提案する — spec が未完のまま prompt を生成すると手戻りが大きい
5. `prompt-rules.md` / `prompt-template.md` を読む
6. spec の操作 / 機能 / 依存関係を分析
7. target / phase で分割 (依存は `depends_on` に実依存で列挙。phase 隣接で近似しない)
8. 各 prompt を `prompt-template.md` に従って生成 (先頭 frontmatter を含む)
9. **セルフ検証**: 各 prompt を絶対ガード (frontmatter + 10 セクション) で突合し、欠落があれば書き直す
10. 生成ファイル一覧と依存関係表を報告

## 生成後の報告

```text
| ファイル          | phase | target     | 並列可 | 依存先 | 概要 |
| ----------------- | ----- | ---------- | ------ | ------ | ---- |
| P1_01_<target>... | 1     | <target-a> | -      | なし   | ...  |
| P2_01_<target>... | 2     | <target-b> | P2_02  | P1_01  | ...  |
```

## 停止条件

- spec の `未確定事項` がゼロでない
- `spec-review` が PASS でない (NEEDS_WORK のまま prompts を作らない)
- target が `context/project.yml` の `domains` から特定できない
- 絶対ガード (frontmatter + 10 セクション) を満たせない prompt が残っている
- 差分修正モードの対象なのに、機能全体を作り直す prompt を生成しようとしている
- 別 app / package の追加探索を要求する prompt になっている (自己完結性違反)
