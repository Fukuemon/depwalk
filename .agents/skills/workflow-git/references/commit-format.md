# コミットメッセージフォーマット

Conventional Commits ベースの日本語コミットメッセージ規約。
コミット実行手順は [git-commit-workflow.md](git-commit-workflow.md) を参照する。

## 基本フォーマット

```
<type>(<scope>): <サマリ> #<issue/ticket番号>

<空行>
変更理由・背景・影響を説明
```

## type 一覧

| type       | 用途                                     |
| ---------- | ---------------------------------------- |
| `feat`     | ユーザーから見える新機能や振る舞いの追加 |
| `fix`      | 不具合修正                               |
| `docs`     | ドキュメント修正                         |
| `refactor` | 振る舞いを変えない設計改善               |
| `test`     | テスト追加・更新                         |
| `chore`    | 保守、設定変更、依存更新などの裏方作業   |
| `ci`       | CI/CD 設定変更                           |
| `build`    | ビルドや依存解決の変更                   |
| `perf`     | 性能改善                                 |
| `style`    | フォーマットや lint 対応                 |
| `revert`   | 変更の取り消し                           |

## ヘッダーの原則

- 1 行目は 50 文字以内を推奨し、最大でも 72 文字程度に収める
- `scope` は任意。文脈が明確になる場合のみ付ける
- ヘッダー末尾に `#123` のような issue / ticket 番号を付ける
- 末尾に句点を付けない
- 破壊的変更がある場合は `feat!:` のように `!` を使う

## 本文の原則

- 自明な typo 修正や format 修正を除き、本文で「なぜ必要だったか」を説明する
- 問題の説明から入り、どう解決したかを続ける
- 数値、エラー、検索結果、合意事項などの根拠があれば積極的に含める
- 72 文字前後で改行する

## issue / ticket 番号の扱い

- 主要な issue / ticket 番号はヘッダー末尾に `#123` として含める
- 複数の関連 issue がある場合や、閉じる意図を明示したい場合だけ本文末尾に補足してよい
- 例:
  - `Refs #123`
  - `Closes #456`

## その他のルール

- 日本語で記述する。技術用語は英語のままでよい
- 技術用語の表記は公式表記に合わせる
- コミットは独立して revert しやすい粒度に分ける
